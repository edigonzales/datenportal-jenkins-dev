== Voraussetzungen

Fuer den lokalen Start werden benoetigt:

* Git
* `curl`
* Java 21 fuer Jenkins
* Java 17 fuer GRETL und den Themenrepo-Wrapper

Modi, Defaults und alle Overrides stehen in der
xref:referenz-konfiguration.adoc[zentralen Konfigurationsreferenz]. Der Hoststart
setzt `JENKINS_RUNTIME_MODE=dev` und die lokale JCasC fest; er startet keine
Produktionskonfiguration.

== Standardstart

```bash
cd ../datenportal-jenkins-dev
./bin/start.sh
```

`bin/start.sh` fuehrt in dieser Reihenfolge aus:

. Java 17 und Java 21 aufloesen;
. das Offline-Bundle bauen oder aktualisieren;
. Jenkins-WAR und Plugin-Manager bei Bedarf herunterladen;
. Jenkins-Plugins aus `plugins.txt` installieren oder aktualisieren;
. native DuckDB-Extensions `postgres`, `spatial`, `excel`, `httpfs` und `s3` für den Host
  installieren beziehungsweise prüfen und den ili2duckdb-Suchpfad einrichten;
. Jenkins mit `casc/jenkins.yaml` starten.

Ein reiner Plugin-Neustart kann das bereits gebaute Bundle wiederverwenden:

[source,bash]
----
SKIP_OFFLINE_BUNDLE=1 ./bin/start.sh
----

`SKIP_OFFLINE_BUNDLE=1` überspringt nur den Bundle-Bau. Plugin-Installation und
Host-Extension-Installation laufen weiterhin; der gesamte Start wird dadurch
nicht garantiert netzfrei.

== Eingangsstand wählen

Lokaler Git-Checkout, ausschliesslich als Vorschau:

[source,bash]
----
THEMEN_REPO_MODE=managed-git THEMEN_REPO_BRANCH=main \
  THEMEN_REPO_WRITE_BACK_ENABLED=false ./bin/start.sh
----

Ohne gesetzte `THEMEN_REPO_URL` verwendet das Skript `file://` auf das lokale
Schwester-Repository. Eine bereits exportierte URL hat Vorrang. Der Default von
`THEMEN_REPO_DIR` ist `../datenportal-themenrepo`; das Skript leitet eine absolute
`file://`-URL daraus ab. Nur eingecheckte Änderungen auf dem gewählten Branch werden
verwendet. Ein HTTPS-Repository kann ausdrücklich über `THEMEN_REPO_URL` gewählt
werden; auch bei dieser Quelle bleibt der Hoststart eine Dev-Laufzeit.

Snapshot einschliesslich nicht eingecheckter Änderungen:

[source,bash]
----
THEMEN_REPO_MODE=working-tree THEMEN_REPO_WRITE_BACK_ENABLED=false ./bin/start.sh
----

Der Quellpfad ist `THEMEN_REPO_PATH`, ersatzweise `THEMEN_REPO_DIR`. In diesem
Modus leert das Skript eine eventuell gesetzte URL. Nach dem Start den Seeder
laufen lassen. Spätere lokale Änderungen werden erst mit einem erneuten Seed
übernommen. Jeder Build arbeitet auf einer eigenen Snapshot-Kopie; weder das
externe Repo noch der Seeder-Snapshot werden verändert. Der Shellstart
aktiviert S3 nicht selbst. Mit separat freigegebenem `s3Publish=true` kann aber
auch dieser Modus nach S3 publizieren; der nächste Lauf liest dann dessen neuen
Gesamtstand. Für die vollständige lokale Integration mit Garage siehe
link:https://codeberg.org/edigonzales/datenportal-dev-stack/src/branch/main/docs/biblios/inbetriebnahme.adoc[Stack-Inbetriebnahme].

Für eine neue ENV-Konfiguration den Hostprozess beenden und erneut starten.
Nach Änderungen an Repository-Modus, URL oder Branch auch den Seeder erneut
ausführen. Ein Seed allein ändert keine Prozessumgebung. Lieferfolgen mit echtem
Commit/Push werden ausschliesslich gegen ein separates lokales Testrepository
geprüft; dafür gibt es den xref:offline-bundle.adoc[Publikations-Image-Test].

== Lokaler Zugriff

Nach dem Start:

* URL: `http://localhost:8080`
* Login: `admin / admin`
* Datenportal-UI: `http://localhost:8080/gretl-datenportal`

Jenkins verwendet in dieser Entwicklungsumgebung den lokalen JCasC-
Security-Realm. Die Testbenutzer werden beim Start aus `casc/jenkins.yaml`
angelegt; eine AD-/LDAP-Umgebung ist für lokale Tests deshalb nicht nötig. In
einer produktiven Installation übernimmt weiterhin die konfigurierte
AD-/LDAP-/Entra-Authentisierung das Anmelden. Das Plugin verwendet für die
Autorisierung die bereits authentisierte Jenkins-Benutzer-ID.

Für Berechtigungstests stehen zusätzlich diese lokalen Konten zur Verfügung:

* `seed-user / seed`: darf den Seeder-Job lesen und starten;
* `read-user / read`: darf freigegebene Organisationsjobs lesen;
* `agi-user / agi`: darf den AGI-Job lesen und starten;
* `mfk-user / mfk`: darf den MFK-Job lesen und starten;
* `statistikdienst-user / statistikdienst`: darf den Statistikdienst-Job
  lesen und starten.

Die Konten erhalten keine globalen `Item`-Rechte. Die tatsächlichen Jobrechte
werden aus `shared/gretl-datenportal-teams.yaml` des Themenrepos synchronisiert.
Die dort eingetragenen IDs müssen zu den Jenkins-Benutzer-IDs passen. Das
Plugin löst die Teams auf und setzt mit `matrix-auth` die projektbezogenen
ACLs; globale `Item/Read`- oder `Item/Build`-Rechte für normale Benutzer sind
in der lokalen Konfiguration nicht vorgesehen.

== Lokale Berechtigungstests

Nach dem ersten erfolgreichen Seed-Lauf können die Konten gezielt geprüft
werden:

* `seed-user / seed` sieht `gretl-datenportal-seed` und darf ihn starten, aber
  nicht konfigurieren;
* `read-user / read` sieht freigegebene Organisationsjobs, darf sie aber nicht
  bauen;
* `agi-user / agi`, `mfk-user / mfk` und `statistikdienst-user / statistikdienst`
  sehen jeweils nur ihren Organisationsjob und dürfen ihn bauen;
* nicht berechtigte Benutzer sehen die jeweiligen Jobs nicht und können sie
  auch nicht über die Jenkins-API starten.

Der Seed-Job ist nach dem Jenkins-Start zunächst nur für `admin` sicher
erreichbar. Nach dem ersten Lauf wird auch seine ACL anhand des konfigurierten
Seeder-Teams synchronisiert.

== Bootstrap nach frischem Checkout

Nach einem frischen Jenkins-Home provisioniert das Plugin den Seed-Job
`gretl-datenportal-seed` nach dem Start selbst. Er wird nicht mehr per JCasC
erzeugt. Wenn ein Themenrepo konfiguriert ist, wird beim ersten Start ohne
bisherigen Seed-Build automatisch ein initialer Seed-Lauf angestossen.

Pflichtablauf:

. Einen Repository-Modus wählen:

** `managed-git`: Änderungen im Themenrepo committen und auf dem von Jenkins
   konfigurierten Branch bereitstellen. Der Seeder aktualisiert seinen
   Jenkins-internen Checkout und verwirft dort lokale Abweichungen.
** `working-tree`: für lokale Entwicklung `THEMEN_REPO_MODE=working-tree` setzen.
   Der Seed-Lauf kopiert den externen Arbeitsbaum inklusive uncommitteter und
   untracked Änderungen in den Jenkins-internen Snapshot. `.git`, `.gradle`,
   `build` und `.DS_Store` werden ausgeschlossen. Das externe Repo bleibt
   unverändert; der Snapshot ändert sich erst beim nächsten Seed-Lauf.
. `./bin/start.sh` ausführen.
. Mit `admin / admin` anmelden.
. Bei einem frischen Home den automatischen initialen Seed-Lauf abwarten. Bei
  einem bestehenden Home oder nach einem fehlgeschlagenen Erstlauf kann
  `gretl-datenportal-seed` weiterhin manuell gestartet werden; alternativ
  wartet man auf den Cron-Lauf.
. Danach mit `seed-user / seed`, `read-user / read`, `agi-user / agi`,
  `mfk-user / mfk` und `statistikdienst-user / statistikdienst` die Seeder-
  und Organisations-ACLs prüfen.
. `/gretl-datenportal` öffnen und die erzeugten Organisationsjobs prüfen.

Die generierten Jobs unter `jenkins-home/jobs` bleiben bewusst lokal und sind
nicht versioniert. Ein bestehender lokaler Job
`gretl-datenportal-plugin-generator-local` kann manuell geloescht werden.

== Lokale Beispieldaten

Das Verzeichnis `data/` enthaelt lokale Beispiel- und Testdateien fuer manuelle
Pruefungen der Entwicklungsumgebung. Diese Dateien sind weder der fachliche
Vertrag des Themenrepos noch die kanonische Plugin-Doku.

Wenn Beispiel-Uploads oder Testdatensaetze fachlich beschrieben werden muessen,
gehoert die strukturierte Erklaerung ins Themenrepo.
